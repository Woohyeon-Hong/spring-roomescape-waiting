# 개선 전 성능 테스트

## 1. 테스트 목적

예약 공개 직후를 가정한 목표 트래픽에서 현재 예약 및 대기 목록 조회 API가 성능 목표를 만족하는지 확인한다.

또한 목표 트래픽을 넘어 요청량을 단계적으로 증가시키면서 응답 시간, 처리량, 오류율이 어떻게 변화하는지 관찰한다.

이번 테스트에서는 현재 구현의 성능 저하 여부와 부하 증가에 따른 변화 양상만 확인한다. 구체적인 병목 원인은 이후 병목 분석을 통해 확인한다.

## 2. 테스트 환경

| 항목     | 값                      |
|--------|------------------------|
| 서버     | AWS EC2                |
| 인스턴스   | t4g.micro              |
| CPU    | 2 vCPU                 |
| 메모리    | 1 GiB                  |
| 애플리케이션 | Spring Boot            |
| 데이터베이스 | H2                     |
| 서버 구성  | 단일 EC2에서 애플리케이션과 H2 실행 |
| 테스트 도구 | Gatling                |

## 3. 테스트 데이터

| 데이터                     |      규모 |
|-------------------------|--------:|
| 전체 예약 수                 | 10,000건 |
| 전체 예약 대기 수              | 30,000건 |
| 대기가 존재하는 슬롯의 평균 대기 수    |     30건 |
| 예약을 보유한 사용자의 평균 예약 수    |      3건 |
| 예약 대기를 보유한 사용자의 평균 대기 수 |      5건 |

테스트 요청은 예약 또는 예약 대기를 보유한 사용자를 대상으로 수행한다.

특정 사용자의 데이터 구성에 결과가 편중되지 않도록, 준비된 사용자 집합에서 요청마다 조회 대상을 선택한다.

## 4. 테스트 대상

```http
GET /reservations
```

요청마다 사용자 인증 정보를 전달하여 해당 사용자의 예약 및 예약 대기 목록을 조회한다.

현재 API는 다음 순서로 요청을 처리한다.

```text
사용자의 예약 목록 조회
→ 사용자의 예약 대기 목록 조회
→ 각 예약 대기의 현재 순번 조회
→ 예약 및 대기 목록 응답 생성
```

## 5. 성능 목표

성능 목표는 목표 트래픽인 18 RPS가 유지되는 동안 만족해야 하는 기준이다.

| 지표        |          목표 |
|-----------|------------:|
| 평균 응답 시간  |    500ms 이하 |
| p95 응답 시간 |  1,000ms 이하 |
| 오류율       |       1% 이하 |
| 평균 성공 처리량 | 17.1 RPS 이상 |

## 6. 테스트 구성

### 6.1. 공통 실행 조건

| 항목       | 값                           |
|----------|-----------------------------|
| 부하 모델    | 초당 요청 도착률 기준                |
| 워밍업 시간   | 30초                         |
| 부하 증가 시간 | 30초                         |
| 부하 유지 시간 | 2분                          |
| 요청 타임아웃  | 60초                         |
| 반복 횟수    | 부하 테스트 2회, 스트레스 테스트 요청량별 1회 |

각 테스트는 다음 순서로 진행한다.

```text
30초 동안 2 RPS로 워밍업
→ 30초 동안 목표 요청량까지 점진적으로 증가
→ 목표 요청량을 2분 동안 유지
```

성능 지표는 워밍업과 부하 증가 구간을 제외하고, 목표 요청량을 유지한 2분 구간을 기준으로 측정한다.

각 테스트는 동일한 환경과 데이터 조건에서 수행한다. 테스트 사이에는 진행 중인 요청이 모두 종료되고 서버의 CPU 및 메모리 사용량이 테스트 전 수준으로 돌아온 것을 확인한 후 다음 테스트를 수행한다.

목표 트래픽에서 측정한 결과가 일시적인 변동이 아닌지 확인하기 위해 부하 테스트는 2회 수행한다. 
두 결과가 유사하면 각 지표의 평균을 대표값으로 사용한다. 
결과 차이가 큰 경우 서버 상태를 확인한 뒤 해당 테스트를 추가로 수행한다. 
스트레스 테스트는 요청량별로 1회 수행하며, 성능 변화의 경계가 불명확하거나 결과에 비정상적인 변동이 나타난 경우 해당 요청량의 테스트만 추가로 수행한다.

### 6.3. 스트레스 테스트

목표 트래픽을 넘어 요청량을 단계적으로 증가시키면서 성능 저하가 심화되는 양상을 확인한다.

| 항목    | 값                    |
|-------|----------------------|
| 요청량   | 20 RPS, 25 RPS       |
| 비교 기준 | 부하 테스트의 18 RPS 대표 결과 | 
| 실행 방식 | 요청량별 독립 실행           |

각 요청량은 하나의 연속된 테스트가 아니라 독립된 테스트로 수행한다.

```text
20 RPS 테스트
→ 서버 상태 안정화
→ 25 RPS 테스트
```

이를 통해 이전 요청량에서 발생한 요청 대기나 자원 사용이 다음 요청량의 결과에 누적되는 것을 줄인다.
