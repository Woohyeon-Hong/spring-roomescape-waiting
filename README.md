# 결제 기능 도입 및 예약 대기 정책 변경

## 1. 예약 결제 기능을 도입한다

---

### 기존 동작

* 사용자가 예약 생성을 요청하면 예약이 즉시 확정된다.
* 결제 과정과 주문 정보는 존재하지 않는다.

### 변경 후 동작

1. 사용자가 예약을 요청한다.
2. 서버는 결제 전에 주문번호와 최종 결제금액을 저장한다.
3. 사용자는 Toss Payments 결제창을 통해 결제를 인증한다.
4. 서버는 전달받은 결제금액을 저장된 주문금액과 비교한다.
5. 금액이 일치하면 결제 승인 API를 호출한다.
6. 결제가 승인되면 결제 정보를 저장하고 예약을 `CONFIRMED` 상태로 변경한다.
7. 결제에 실패하면 예약을 확정하지 않고 실패 상태를 처리한다.

### 기능 요구사항

* [ ] 결제 인증 전에 주문 정보인 `orderId`와 최종 결제금액을 저장한다.
* [ ] `orderId`는 서버에서 생성하며 다음 조건을 만족해야 한다.

    * [ ] 길이는 6자 이상 64자 이하이다.
    * [ ] 영문자, 숫자, `-`, `_`만 사용한다.
* [ ] 예약 페이지에서 Toss Payments 결제창을 제공한다.
* [ ] 서버는 카드번호와 같은 카드 결제수단 정보를 직접 저장하거나 처리하지 않는다.
* [ ] 결제 결과로 전달된 금액을 그대로 신뢰하지 않고, 서버에 저장된 주문금액과 비교한다.
* [ ] 금액이 일치하는 경우에만 결제 승인을 요청한다.
* [ ] 결제가 승인되면 다음 정보를 처리한다.

    * [ ] 조회와 취소에 필요한 `paymentKey`를 저장한다.
    * [ ] 주문을 결제 완료 상태로 변경한다.
    * [ ] 예약을 `CONFIRMED` 상태로 변경한다.
* [ ] 동일한 결제에 대한 중복 승인 요청을 방지해야 한다.
* [ ] 결제 실패 사유를 사용자에게 제공한다.
* [ ] 결제 실패 시 주문과 예약을 사전에 정의한 실패 상태로 변경한다.
* [ ] 사용자 취소로 `orderId`가 전달되지 않는 경우에도 예외 없이 실패 화면을 제공한다.


## 2. 예약 대기 승격 방식을 변경한다

---

### 기존 동작

예약이 취소되거나 변경되면 동일한 슬롯의 첫 번째 예약 대기가 자동으로 예약으로 승격된다.

### 변경 후 동작

예약 대기는 자동으로 예약으로 승격되지 않는다.

예약 가능한 슬롯이 발생하면 승격 가능한 예약 대기 정보를 사용자에게 제공하고, 사용자가 직접 해당 슬롯의 예약과 결제를 진행한다.

### 기능 요구사항

* [ ] 예약 취소 또는 변경 시 예약 대기를 자동으로 예약으로 전환하지 않는다.
* [ ] 예약 가능한 슬롯과 일치하는 예약 대기를 조회할 수 있어야 한다.
* [ ] 사용자는 승격 가능한 예약 대기를 확인할 수 있어야 한다.
* [ ] 사용자는 해당 예약 대기를 기반으로 새로운 예약을 생성할 수 있어야 한다.
* [ ] 새 예약도 일반 예약과 동일하게 결제 과정을 거쳐야 한다.
* [ ] 결제가 완료된 경우에만 예약을 확정하고 기존 예약 대기를 제거한다.
* [ ] 결제에 실패하거나 취소한 경우 기존 예약 대기를 유지한다.
* [ ] 여러 예약 대기 사용자 중 예약을 시도할 수 있는 대상과 유효기간을 정의해야 한다.

## 공통 구현 요구 사항

---

* Toss Payments 결제 승인 API를 서버에서 호출한다.
* 결제 승인 API 호출에는 `RestClient`를 사용한다.
* 시크릿 키는 코드에 하드코딩하지 않고 외부 설정으로 관리한다.
* 결제 외부 연동은 `PaymentGateway` 인터페이스를 통해 추상화한다.
* 애플리케이션 계층은 Toss Payments 전용 DTO와 구현 세부사항에 의존하지 않는다.
* 외부 결제 오류는 애플리케이션에서 정의한 결제 예외로 변환한다.
